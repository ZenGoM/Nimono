## 改善点 1: 消えたファイルのキャッシュが削除されず、DB が増え続ける

### 現状

`CacheManager.cs` が `ImageCache` 表から行を消すのは、次の 2 つの場合だけ。

- 「キャッシュをクリア」したとき（`ClearCache`）
- スキーマの版（`SchemaVersion`）が上がったとき（`Initialize`）

削除・移動・名前変更したファイルの行はずっと残る。

### 影響

- DINOv2 は 1 枚あたり 4 つの向きの埋め込みを持つため、1 行が「次元数 × 4 × 4 バイト」になる（768 次元なら約 12 KB）。
- 比較画面で重複を削除するのがこのアプリの主な使い方なので、使うほど DB に不要な行がたまる。

### 対応案

- スキャンの最後に、今回スキャンしたフォルダーの中にあるのに見つからなかったパスの行を削除する。
- キャッシュはフォルダーをまたいで共有しているため、今回スキャンしなかったフォルダーの行は消さない。
- 削除した行数が多いときは `VACUUM` も実行して、ファイルを縮める。

## 改善点 2: 似ていない画像同士が、連鎖して同じグループになる

### 現状

`ImageGrouper.Connect`（`ImageGrouper.cs` 524〜539 行）は、似ている組を見つけるたびに Union-Find でつなぐ（単連結）。
A と B が似ていて、B と C が似ていれば、A と C が似ていなくても同じグループになる。

### 影響

- しきい値を下げたときや、連写・似た構図の写真が多いときに、大きなグループができやすい。
- 比較画面の類似度は基準画像との比較（`MatchToReference`）なので、しきい値を下回る画像が同じグループに並ぶことがある。

### 対応案

次のどちらかを検討する。

- グループの全員が基準と似ていることを条件にする（基準を中心にした分け方）。
- 少なくとも、基準との類似度がしきい値を下回る画像を、一覧で目立たせる。

グループの分け方そのものが変わるため、SPEC.md の更新が必要。
グループキャッシュ（`PlanWithCache`）も、つなぎ方に合わせて見直す必要がある。

## 改善点 3: キャッシュのエラーを何も表示せず無視している

### 現状

`CacheManager.cs` の読み込み・保存・クリアは、どれも `catch { }` で例外を握りつぶしており、ログも出していない（コード全体では、このような `catch` が 32 か所ある）。

### 影響

次のような場合に、利用者には「なぜか毎回遅い」としか見えない。

- DB が壊れている
- 他のプロセスが DB を開いている
- キャッシュの場所を外付けドライブにしていて、そのドライブが外れている

保存に失敗しても誰も気づかないので、次回もすべて計算し直しになる。

### 対応案

- 最低限、例外を `ScanLogger` に記録する。
- 読み込みや保存に失敗したときは、ステータスバーに「キャッシュを使えませんでした（理由）」と一行出す。
