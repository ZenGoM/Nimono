# Nimono 仕様書 — メイン画面

## 1. 概要

Nimono は Windows デスクトップ向けの画像類似検索・グルーピングアプリケーションです。
指定したフォルダー以下の画像ファイルを再帰的に探索し、画像の内容に基づいて類似した画像をグループ化します。
グループ化結果をサムネイル一覧で表示し、類似画像の確認・比較を支援します。

## 4. ツールバー

| コントロール | 動作 |
|------------|------|
| `フォルダー選択...` | `SearchFolderDialog` を開き、スキャン対象フォルダーを追加・削除する |
| `スキャン開始` | スキャンを開始する。フォルダー未選択時は無効 |
| `計算方式` | ドロップダウン。`pHash（高速）` / `DINOv2 CPU` / `DINOv2 GPU (DirectML)` から選択 |
| `類似度しきい値` | 50〜100 の整数（%）を入力。デフォルト 85。変更時に設定を即保存 |
| `キャッシュ` | メニューを開く（場所を変更 / 場所を既定に戻す / 場所を開く / キャッシュをクリア）。ボタン名に現在のキャッシュ容量を動的に表示する（例: `キャッシュ (12.3 MB)`）。クリアは確認ダイアログあり。スキャン中は無効 |
| `キャンセル` | スキャン中のみ有効。処理を中断する |

## 5. スキャン処理

- 「スキャン開始」ボタンで開始する。
- 起動時は、前回のフォルダーが 1 つ以上選択済みなら、画面が表示された時点（`Shown`）で自動的にスキャンを開始する。
  「N フォルダー選択中 — 「スキャン開始」を押してください」の案内は出さない。フォルダーが未選択なら自動では開始しない。

### 5.1 処理ステップ（pHash モード）

| ステップ | 処理内容 | 担当クラス |
|---------|---------|-----------|
| 1 | フォルダーを再帰走査して画像ファイルを列挙 | `ImageGrouper.EnumerateImages` |
| 2 | キャッシュ DB からメモリに読み込み（特徴量キャッシュ・グループキャッシュ） | `CacheManager.LoadCacheAsync` / `LoadGroupCacheAsync` |
| 3 | 各画像の 64bit pHash を並列計算（キャッシュヒット時はスキップ） | `ImageGrouper.ComputeHashes` |
| 4 | ハミング距離でグループ化（Union-Find）。グループキャッシュで使える部分は比較を省く（→ 6.4） | `ImageGrouper.Group` |
| 5 | 新規・変更分の特徴量キャッシュと、今回のグループキャッシュを DB に保存 | `CacheManager.SaveCacheAsync` / `SaveGroupCacheAsync` |
| 6 | 結果をメイン画面に表示 | `MainForm.RenderGroups` |

### 5.2 処理ステップ（DINOv2 モード）

| ステップ | 処理内容 | 担当クラス |
|---------|---------|-----------|
| 1 | フォルダーを再帰走査して画像ファイルを列挙 | `ImageGrouper.EnumerateImages` |
| 2 | キャッシュ DB からメモリに読み込み（特徴量キャッシュ・グループキャッシュ） | `CacheManager.LoadCacheAsync` / `LoadGroupCacheAsync` |
| 3 | 各画像の DINOv2 埋め込みベクトルを並列計算（キャッシュヒット時はスキップ） | `ImageGrouper.ComputeEmbeddings` |
| 4 | コサイン類似度でグループ化（Union-Find）。グループキャッシュで使える部分は比較を省く（→ 6.4） | `ImageGrouper.GroupByEmbedding` |
| 5 | 新規・変更分の特徴量キャッシュと、今回のグループキャッシュを DB に保存 | `CacheManager.SaveCacheAsync` / `SaveGroupCacheAsync` |
| 6 | 結果をメイン画面に表示 | `MainForm.RenderGroups` |

- ステータスバーの文言は幅が足りない場合、折り返さずに末尾を「…」で省略する。

## 6. キャッシュシステム

### 6.1 概要

スキャン結果を SQLite データベースにキャッシュし、再スキャン時に計算をスキップする。キャッシュはファイルサイズと最終更新日時をキーとして有効性を判定する。

| キャッシュ | 内容 | 省ける処理 |
|-----------|------|-----------|
| 特徴量キャッシュ（6.3） | ファイルごとの pHash / DINOv2 埋め込みベクトル | 特徴量の計算 |
| グループキャッシュ（6.4） | 前回スキャンのグルーピング結果 | 変わっていないファイル同士の比較 |

### 6.2 キャッシュ DB

- 保存先: 既定は `%LOCALAPPDATA%\Nimono\cache.db`。「キャッシュ」→「キャッシュの場所を変更...」で任意のフォルダー（その直下の `cache.db`）に変えられ、設定 `CacheFolder` に保存する（空 = 既定）
- 場所を変えるときは、今の DB（`-wal` / `-shm` を含む）を移動先へ移す。移動先に既に DB があれば、上書きするか、移動先の DB をそのまま使うか（今の DB は元の場所に残す）を選ぶ
- 移動の前に `SqliteConnection.ClearAllPools()` でプールの接続を閉じる（開いたままだとファイルを動かせない）
- 形式: SQLite
- 管理クラス: `CacheManager`

### 6.3 特徴量キャッシュ（`ImageCache` 表）

| フィールド | 型 | 内容 |
|-----------|-----|------|
| `Path` | `string` | ファイルのフルパス（主キー） |
| `FileSize` | `long` | ファイルサイズ（バイト） |
| `LastWriteTimeTicks` | `long` | 最終更新日時（Ticks） |
| `PHash` | `ulong?` | pHash 値（未計算なら null） |
| `Embedding` | `float[]?` | DINOv2 埋め込みベクトル。0°・90°・180°・270° に回した画像の 4 本を連結したもの（→ §10.3）（未計算なら null） |

- 計算方法を変えたときは、DB の `PRAGMA user_version`（`CacheManager.SchemaVersion`）を上げる。
  開いた DB の版が古ければ、特徴量キャッシュとグループキャッシュを捨てて計算し直す。
  - 版 2: ハッシュ・埋め込みを EXIF の向きに合わせてから計算し、埋め込みは 4 つの向きの分を持つ。

### 6.4 グループキャッシュ（`GroupCache` 表・`GroupCacheInfo` 表）

グルーピングは全ファイルの組み合わせ（n² 通り）を比べるため、ファイル数が多いと特徴量がキャッシュ済みでも時間がかかる。
前回スキャンの結果を覚えておき、変わっていない部分の比較を省く。

**保存する内容**

方式（`pHash` / `DINOv2`）ごとに、前回スキャンの 1 回分だけを持つ。スキャンが終わるたびにその方式の分を丸ごと入れ替える。
DINOv2 の CPU / GPU は同じ埋め込みキャッシュを使うため、グループキャッシュも共通とする。

| 表 | フィールド | 内容 |
|----|-----------|------|
| `GroupCacheInfo` | `Mode` | 方式（主キー） |
| | `Threshold` | そのときのしきい値 |
| `GroupCache` | `Mode` / `FilePath` | 方式とファイルのフルパス（主キー） |
| | `FileSize` / `LastWriteTimeTicks` | そのときのファイルサイズ・最終更新日時 |
| | `GroupKey` | 所属したグループ。どのグループにも属さなかったファイルは null |

グルーピングの対象になったファイルは、グループに属さなかったものも含めてすべて保存する。

**使い方**

| 条件 | 扱い |
|------|------|
| キャッシュが無い・しきい値が前回と違う | 使わない（全件を比較する） |
| 前回に無かったファイル、サイズか更新日時が変わったファイル | 比較し直す |
| メンバー全員が今回も対象で、どれも変わっていないグループ | そのまま 1 つのグループとして使う |
| 変わったファイル・今回無いファイル（削除・対象外のフォルダー）を 1 つでも含むグループ | キャッシュを使わず、メンバー全員を比較し直す |
| 前回どのグループにも属さず、変わっていないファイル | 比較し直すファイルとの間だけ比べる |

- 比較するのは「比較し直すファイル × 全ファイル」だけで、結果は全件を比較し直した場合と同じになる。
  - 変わっていないファイル同士の関係は前回と同じため、比べる必要がない。
  - 欠けたファイルがグループの橋渡しになっていた場合はグループが割れうるため、欠けたグループは作り直す。
- 前回と違うフォルダーをスキャンした場合、前回に無かったファイルはすべて比較し直しになる（結果は正しいが速くはならない）。
- 「キャッシュ」ボタンでのクリアは、特徴量キャッシュと一緒にグループキャッシュも消す。

## 7. グループ表示

### 7.1 グループの定義

- **pHash モード**: ハミング距離 ≤ `floor(64 × (1 − T))` の画像を Union-Find で統合
- **DINOv2 モード**: コサイン類似度 ≥ T の画像を Union-Find で統合
- どちらも、向きが違うだけ（90° 単位の回転）の画像は同じ画像とみなす。4 つの向きのうち最も近い向きで比べる（→ §9・§10.3）
- 類似度の計算は `ImageGrouper.MatchToReference` にまとめ、グルーピング・メイン画面での基準変更・比較画面で同じ値になるようにする
- 2 枚以上の画像を含むグループのみ表示
- グループは画像枚数の多い順に表示

### 7.2 グループヘッダー

- 背景色: `RGB(60, 90, 140)`（青系）/ 高さ 28px
- テキスト: `グループ {ID} — {枚数} 枚`
- 右端に「比較」ボタン（クリックで比較画面を開く → [COMPARE_SPEC.md](COMPARE_SPEC.md)）
- その左に「基準以外を削除」ボタン。基準画像だけを残し、ほかの画像（表示しきれていない画像も含む）をまとめて削除する
  - 「次回以降確認しない」に関係なく、必ず 1 回確認する。確認には基準と、ゴミ箱に移動するファイル・完全に削除するファイル（`NoRecycleProviders` のクラウド同期フォルダー内）を分けて並べる（各 10 件まで）
  - 完全に削除するファイルはこの確認で了承済みとして、個別には確認しない。ゴミ箱への移動が予期せず失敗したファイルだけ、比較画面と同じ「完全に削除しますか？」を 1 件ずつ確認する
  - すべて削除できればグループを取り除く。中止・失敗で 2 枚以上残れば、残りでグループを作り直す
  - 削除処理は比較画面と共通（`FileDeleter`）

### 7.3 グループ内の画像順序

- 基準画像（最も高い類似度 = 100%）が先頭
- 以降は基準画像との類似度の降順
- サムネイルをクリックすると、クリックした画像が新たな基準となり再ソート

### 7.4 仮想スクロール（遅延パネル生成）

大量グループ（例: 12,000+ グループ）が存在する場合のパフォーマンスを確保するため、仮想スクロールと遅延パネル生成を採用しています。

- `RenderGroups` ではパネルを生成せず、各グループの高さを**推定**して絶対位置（`_groupTops`）を記録
- `AutoScrollMinSize` を推定総高さに設定してスクロールバーを制御
- 表示領域 ± 1 viewport 分のグループが可視域に入った時点で初めて `BuildGroupPanel` を呼び出し、パネル・サムネイルを生成する
- 実測高さが推定と異なる場合は、後続グループの位置を自動的に再計算する
- 表示領域から 3 viewport 以上離れたパネルは破棄してメモリを解放する
- スクロールイベント（`WM_VSCROLL` / `WM_MOUSEWHEEL` / `WM_KEYDOWN`）で表示グループを更新

**サムネイルの非同期読み込み**

サムネイル画像の生成は 1 件あたり約 150ms（1,200 万画素の JPEG を展開して縮小）かかり、UI スレッドで行うとスクロールが止まる。
そのためパネル生成時は次のように分ける。

| 処理 | 実行場所 | 所要時間の目安 |
|------|---------|---------------|
| ヘッダーだけ読む（縦横・EXIF の向き・日付）→ カードの大きさと情報欄を決める | UI スレッド（パネル生成時） | 1 件 1ms 程度 |
| サムネイル画像を作る（§8.2）→ できしだい PictureBox に差し込む | バックグラウンド | 1 件 150ms 程度 |

- カードの大きさはヘッダーの縦横（EXIF の向きと保存済みの回転を反映）で先に決めるため、サムネイルが届いても並びは動かない。届くまでは灰色の枠を表示する。
- 同時に生成するのは CPU コア数の半分（最低 2）まで。
- 順番待ちの間にスクロールでカードが破棄された場合は生成せずに飛ばす。届いた時点でカードが破棄されていれば捨てる。

## 8. サムネイル

### 8.1 表示構成（上から順）

| 要素 | 内容 | 高さ |
|------|------|------|
| 類似度ラベル | `類似度: 94%`（基準画像は `【基準】`）。Segoe UI 9pt 太字 | 18px |
| PictureBox | 縦 140px（枠線 1px を含む）、横幅は画像の縦横比なり、`StretchImage` モード | 140px |
| ファイル名ラベル | 切り捨て表示、クリック可 | 18px |
| 情報ラベル | 形式・サイズ / 解像度 / 日付 / ディレクトリパス | 可変 |

基準以外の画像では、ファイル名ラベルと情報ラベルのうち基準画像と違う部分を赤（RGB 200,0,0）で表示する（比較画面と同じ規則、`DiffText`）。
ファイル名とディレクトリパスは文字単位で比べ、共通の前後を除いた中間部分だけを赤くする。形式・サイズ・解像度・日付は項目単位で比べ、違えば項目全体を赤くする。
部分的に色を変えるため、両ラベルは `DiffLabel`（自前描画）で描く。ファイル名は 1 行で、はみ出す分を「…」で省略する。情報ラベルは空白の位置で折り返し、1 単語が収まらないときは文字単位で折り返す。

サムネイル全体の幅: PictureBox の横幅と 140px の大きい方 + 余白 8px（縦長の画像でも最低 148px）。
画像の上下に余白が出ないよう、PictureBox の横幅は画像に合わせて決める。右クリックの「回転」で縦横が入れ替わったときも決め直す。
枠線の内側（縦 138px）をサムネイルと同じ大きさにそろえ、`StretchImage` で描く。
`Zoom` は縮小率の丸めで絵が 1px 小さくなり、下に隙間が出るため使わない。

### 8.2 サムネイル画像の生成（`Thumbnail`）

- 大きさは元画像の縦横比を保ち、縦幅を 138px（PictureBox の枠線の内側）に合わせる。横幅は縦横比なりとする。等倍で描くため、表示時に縮小しない。
- EXIF の埋め込みサムネイルが使える場合は GDI+ の `GetThumbnailImage()` に任せる。展開が要らないため速い。
- ただし次のいずれかに当てはまる埋め込みは使わず、本体から縮小する。
  - **本体と縦横比が 2% を超えて違う**もの。4:3 の枠に縦位置の写真を黒帯付きで収めた埋め込みを持つ機種があり、
    `GetThumbnailImage()` はそれを要求サイズまで引き伸ばすため、黒帯ごと歪んだ絵になる
    （例: 本体 480 × 854 に対し埋め込み 160 × 120）。
  - **要求サイズより小さい**もの。引き伸ばすと粗くなるため。
- 埋め込みの大きさは JPEG のヘッダー（SOF）から読む。判定のために展開はしない。
- EXIF の向き（Orientation）に合わせて回してから返す（`ImageOrientation`）。90 度回す写真は、
  回したあとに枠へ収まるよう縦横を入れ替えて大きさを決める。
- 右クリックの「回転」（§8.5）で保存した回転は、EXIF の向きを反映したあとに重ねて適用する。

### 8.3 情報ラベルの内容

```
JPG · 1.2 MB
1920×1080
2024/01/15
C:\path\to\dir
```

**日付（`ImageDate`）**

以下の順に探し、最初に見つかった値を `yyyy/MM/dd` で表示する。比較画面（→ [COMPARE_SPEC.md](COMPARE_SPEC.md)）も同じ規則で表示する。

| 順 | 取得元 |
|---|---|
| 1 | EXIF `DateTimeOriginal`（0x9003・撮影日時） |
| 2 | EXIF `DateTimeDigitized`（0x9004・デジタル化日時） |
| 3 | EXIF `DateTime`（0x0132・ファイル変更日時） |
| 4 | ファイルの更新日時（EXIF を持たない形式・GDI+ が扱えない形式・読み取り失敗時） |

- コピーやダウンロードで更新日時が変わっても、撮影した日で見比べられるようにするため。
- EXIF の日時は `yyyy:MM:dd HH:mm:ss` の形式で読む。形式が違う値は無視して次の候補へ進む。
- メイン画面ではサムネイル生成のために開いた画像からそのまま読む（ファイルを開き直さない）。

## 9. 画像ハッシュアルゴリズム（pHash）

1. 画像を 8×8 ピクセルに縮小（HighQualityBicubic）し、EXIF の向き（Orientation）に合わせて回す
2. グレースケール変換: `0.299R + 0.587G + 0.114B`
3. 64 ピクセルの平均輝度を計算
4. 各ピクセルが平均以上なら 1、未満なら 0 の 64bit ハッシュを生成

```
ハミング距離  = min over r ∈ {0,1,2,3} PopCount(hash1 ^ rot90^r(hash2))
類似度        = 1.0 − distance / 64.0
最大距離閾値  = floor(64 × (1 − T))   ※ T = 類似度しきい値
```

- `rot90` はハッシュの 8×8 の格子を右に 90° 回す（`ImageHasher.Rotate90`）。8×8 に縮めてから回しても、回してから縮めたのと同じになるため、画像を読み直さずに回した画像のハッシュが得られる。
- 最も近かった r が、その画像を基準の向きにそろえるための回転（右回り 90° × r）。比較画面の表示に使う（→ COMPARE_SPEC.md §9）。
- グルーピングでは、全件の 4 つの向きのハッシュを先に作っておき、組ごとには作らない。

## 10. DINOv2 アルゴリズム

### 10.1 概要

DINOv2 は Meta が開発した自己教師あり学習モデルで、画像の意味的な特徴を捉えた埋め込みベクトルを生成する。pHash よりも高精度な類似画像検出が可能。

### 10.2 処理フロー

1. 画像を 224×224 ピクセルにリサイズ（Bilinear）し、EXIF の向き（Orientation）に合わせて回す
2. それを 0°・90°・180°・270°（右回り）に回した 4 枚を作る（正方形に縮めてから回しても、回してから縮めたのと同じ）
3. ImageNet の平均・標準偏差で正規化（BGR → RGB 変換込み）
4. ONNX Runtime でモデルを実行し、CLS トークンの埋め込みベクトルを取得（4 枚をまとめて推論。GPU では 2 枚分 = 8 テンソルを 1 バッチ）
5. それぞれ L2 正規化し、4 本を向きの順に連結して 1 つの埋め込みとして持つ

推論の回数は 1 枚あたり 4 回、埋め込みの大きさも 4 倍になる。

### 10.3 類似度計算

```
コサイン類似度 = max over r ∈ {0,1,2,3} dot(a[0°], b[r × 90°])   ※ 各ベクトルは L2 正規化済み
```

- `a` は 0° のベクトルだけを使い、`b` の 4 つの向きと比べる（a を回した場合も、向きの差が同じなら同じ値になるため）。
- 最も近かった r が、その画像を基準の向きにそろえるための回転（右回り 90° × r）。
- グルーピングでは、どれかの向きでしきい値に届いた時点で打ち切る。比較の回数が最大 4 倍になるため、内積は SIMD（`Vector<float>`）で計算する。

### 10.4 モデルファイル

- 形式: ONNX（`.onnx`）
- 自動検出: 実行ファイルと同じディレクトリの `model.onnx` を自動読み込み
- 実行プロバイダー: CPU または DirectML（GPU）

### 10.5 DirectML（GPU）動作仕様

DINOv2 の埋め込み計算に DirectML を利用する場合の動作仕様は以下の通りです。

- **ONNX Runtime 実行プロバイダー**:
  - 計算方式で「DINOv2 GPU (DirectML)」が選択された場合、ONNX Runtime の `AppendExecutionProvider_DML(0)` を呼び出し、DirectX 12 互換 GPU で推論処理を実行する。
  - DirectML は NVIDIA / AMD / Intel / 統合 GPU を問わず DX12 対応であれば動作し、ベンダー固有ランタイム（CUDA Toolkit / cuDNN）は不要。
  - `GraphOptimizationLevel` は `ORT_ENABLE_BASIC` を使用（DirectML EP との互換性確保）。
- **起動時スモークテスト**:
  - セッション作成直後に全ゼロのダミーテンソル `[1,3,224,224]` で 1 回 `Run()` を実行し、Run 時に発生する DirectML エラー（ドライバ不整合・カーネル不在など）を検出する。
  - 検出した場合はセッションを破棄し、ユーザーに「DirectML (GPU) の初期化に失敗しました」とエラーダイアログを表示してスキャンを中止する（自動 CPU フォールバックは行わない。ユーザーが手動で「DINOv2 CPU」に切り替える）。

### 10.6 DirectML 環境の要件

- **OS**: Windows 10 1709 (RS3) 以降、または Windows 11
- **GPU**: DirectX 12 対応 GPU
- **グラフィックドライバー**: 各 GPU ベンダーの最新ドライバー（DirectML は WDDM 2.x 系に対応）
- **追加インストール**: 不要（DirectML ランタイムは Windows に同梱、追加 DLL は NuGet パッケージ `Microsoft.ML.OnnxRuntime.DirectML` に含まれる）

### 10.7 DirectML の動作確認方法

PowerShell で GPU が DirectX 12 をサポートしているか確認します。

```powershell
dxdiag /t dxdiag.txt
# 出力ファイルの "Feature Levels" に "12_0" 以上が含まれることを確認
```

または、Nimono を起動して計算方式に「DINOv2 GPU (DirectML)」を選び、小さなフォルダーでスキャンを実行することで、起動時のスモークテストが成功するかどうかが判定できる。

## 13. 既知の制約

- pHash は 8×8 の粗いハッシュのため、近似的な一致のみ検出。精度は完全ではない。
- グループ化は O(n²) の全ペア比較のため、画像数が多いほど処理時間が増加する。
- サムネイル読み込み失敗時は灰色の空欄で表示される。
- DINOv2 モードでは ONNX モデルファイルが必要。モデル未設定時はスキャン開始時にメッセージを表示する。
- 仮想スクロールにより Win32 の 32,767px 座標上限を回避している。可視域外のパネルは破棄されるため、スクロール時にサムネイル再生成コストが発生する。
